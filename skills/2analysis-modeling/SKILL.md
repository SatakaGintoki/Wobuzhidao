# 赛题分析与建模设计

先读取 [审核与逐问推进规则](../_references/review_workflow.md)。本阶段有“整体路线”和“当前问详细方案”两种调用范围：整体阶段执行 Step 1–3 并提交路线审核；通过后，每次仅对当前问执行 Step 4–5，再提交本问方案审核。后续问题只列方向及依赖，不能提前定稿全部方案。

同时读取 [文献参与建模规则](../_references/literature_support.md)。检索在模型选择前和逐问方案形成时进行，文献依据随现有方案一起审核，不增加独立审批。

## 开放选型与方案层次

模型清单仅供参考，不限制候选范围。不得因未收录排除方法，或因已收录、熟悉、复杂、新颖而优先采用。可以根据题目机制自行推导没有固定名称的模型，也可采用外部文献中的方法或改造已有模型。

先分析目标、已知/未知量、可控变量、关系和硬约束，形成初步数学表达，再结合领域检索、数据检查和适用条件形成候选。表达和检索允许迭代，不必在读文献前就定死模型，也不能拿模型名称代替题目分析。

每份详细方案分清四层：问题如何抽象；数学模型的变量、关系与假设；求解算法为何适合该结构和预算；如何验证模型有效、计算正确。知识库的防错清单按实际方法读取，不用题型标签直接决定算法。

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md` 中的“赛题理解与子问题识别”“假设与模型建立”和“题型防错速查”小节。该文件只作为规范知识库，不替代本阶段的分析报告结构。

## 必须产出

在当前工作目录的 `reports/` 子目录中创建或更新：

- `reports/ANALYSIS_MODELING_REPORT.md`：
  - 赛题分析、子问题拆解、数据与附件理解、评价标准、关键歧义和假设预检。
  - 变量、符号、模型假设、目标函数、约束条件、求解算法、各子问题实现口径、代码阶段任务清单
- `reports/LITERATURE_REPORT.md`：相关来源、实际读取范围、支持的具体主张、本题适用差异、引用核实状态及证据缺口。

按调用范围增量更新报告，标明方案版本和审核状态，保留已通过问题的内容。不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。


## 工作流程


### Step 1: 子问题拆解

只把题面中明确编号的顶层问题当作子问题，例如“问题一/二/三”“Problem 1/2/3”。不要把小问、背景描述、数据说明、提交要求误当成独立子问题。

在 `ANALYSIS_MODELING_REPORT.md` 开头明确写：

根据题目动态调整问题数量

本赛题共 X 个子问题。

每个子问题要说明：

- 输入数据和已知条件。
- 决策变量或预测对象。
- 目标函数或评价指标。
- 约束条件。
- 与其它子问题的依赖关系。
- 绘制哪些图像或表格来展示结果。

### Step 2: 假设敏感性预检

列出关键歧义，不要急着定模型。对影响结果的歧义至少给出两种解释，并用简单验算或逻辑递进判断选择。

必须在 `ANALYSIS_MODELING_REPORT.md` 中包含：

```markdown
## 假设敏感性预检

### 模糊表述及解释
...

### 快速验算与递进性检查
...

### 最终采用的解释
...

### 绘制的图像和对比表格


```

如果某个假设会让后续问题的新增条件没有边际效果，要回头调整解释.

### Step 3: 数据理解与建模路线

对每份附件做数据理解：

- 行列规模和字段解释。
- 缺失、异常、重复、单位不一致。
- 可直接用于建模的变量。
- 需要派生的指标。

结合数据条件检索相关领域研究，比较常见方法及其适用前提和局限。复用已有核实资料，不只围绕先选中的模型找支持性文章；记录可能否定候选路线的证据。

在路线中说明要保留的关键机制、可控与不可控因素及初步关系，允许不同于知识库分类的表述。模型候选可来自领域研究、自行推导或本地参考，按同一标准判断，不要求各来源都凑一个方法。

在文献报告中保存关键来源与检索限制后，给出有依据的总体路线：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> 。。。。 -> 结果检验 -> 论文展示
```

### Step 4: 建模报告

确认整体路线已通过且前问最终结果有效，在 `ANALYSIS_MODELING_REPORT.md` 中写出当前问可实现的方案，并列出采用的前问结果版本。输入不足或前问结果失效时先解决依赖，不据猜测推进。

按 [跨问记录与上下文恢复](../_references/context_memory.md) 实际重读相关前问模型记录和源材料，在本问方案开头给出“沿用前问内容”表，核对版本、数据口径、单位与适用限制。形成待审方案及收到批准/修改决定时同步维护本问模型记录和状态索引；被否决的重要路线保留原因。

先给成熟、可实现的稳健方案；有实际提升空间时给探索选项，比较题目依据、假设、解释性、成本、风险及验证方法。探索不限定为更复杂的算法，也可以改进约束表达、利用题目信息或处理不确定性。建议投入上限和停止条件，交由用户决定是否开展。

稳健指假设合理、实现可行且能验证，不等于必须使用有固定名称的常见模型。探索必须针对稳健路线的具体不足；没有实质差异或改进空间时说明原因，不强行凑两条路线或清单外方法。

在方案中列出简短比较表：候选及数学表达、适用依据、关键假设/遗漏机制、不适用条件、验证或放弃标准、实现成本、建议采用或排除理由。对于尚不能判断的候选，提出有边界的小规模可行性验证，不宣称未经比较的方法为全局最佳。

对当前问的关键模型、非显然假设、经验公式和外部参数定向补查。在报告加入“建模依据”表：主张/模型要素、题面给定或文献支持或自行推导、来源标识与内容位置、适用条件、本题差异与改造、核实状态及验证办法。不能把“某文献用过”当成“本题适用”的证明；缺少直接先例的原创方案用推导与实验支撑，不强配论文。

当前子问题先说明目标、输入输出、依据和验证方式，再按实际任务填写适用项：

| 任务 | 应展开的内容 |
|---|---|
| 优化决策 | 决策变量、目标函数、约束、求解及可行性/求解质量验证 |
| 预测或统计分析 | 分析/预测对象、统计口径、模型或检验、假设与误差/不确定性；不虚构优化目标 |
| 解释或建议 | 证据链、建议依据、适用边界、评价与优先级；只有确需计算时才安排代码 |

下列为适用字段清单，不要求每题全部填满；不适用项可简述理由：

- 问题目标。
- 符号和变量。
- 模型假设。
- 目标函数。
- 约束条件。
- 求解方法。
- 输入输出。
- 代码实现要点。
- 结果校验方法。
- 稳健方案与探索选项的区别、建议投入范围及停止条件。
- 文献支持的具体部分、本题迁移条件与改造点，以及尚未核实的依据。
- 问题抽象、数学模型、求解算法与验证方法的对应关系；候选的选用/排除理由与放弃标准。

需要计算时，公式应清楚到代码阶段能实现，算法说明核心步骤、停止条件和计算可行性。建议/解释题仍经过本问方案和结果审核，可直接形成有依据的建议结果，不强制进入数值求解或生成图表。

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 数据处理方案
## 3. 符号说明
## 4. 问题一模型
## 5. 问题二模型
## 6. 问题三模型
    .... 
## 7. 灵敏度分析与检验方案
## 8. 代码实现任务清单
```

如果子问题数量不是 3 个，按实际题面调整章节，不要硬凑。上述是累计报告目录；未轮到的问题只保留已讨论方向，不提前填造详细方案。

### Step 5: 给代码阶段的接口

在 `ANALYSIS_MODELING_REPORT.md` 末尾写一个“代码实现任务清单”，格式如下：

```markdown
## 代码实现任务清单

| 任务 | 输入 | 输出 | 方法 | 校验 |
| --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... |
```


## 质量要求

- 依据区分题面给定、已核实文献和自行提出/推导；结论能够追溯到相应证据或验证，不混淆三者。
- 不编造数据字段和数值。
- 不跳过歧义分析。
- 模型既要有数学表达，也要能被代码实现。
- 若数据不足或题面不清，要明确记录风险和替代方案。
- 完成整体路线或本问方案材料后，在 `reports/REVIEW_LOG.md` 记为 `PENDING` 并提交用户审核；批准后记录具体方案版本、选择与探索范围，再交接编码。报告完整不等于获得实施授权。
- 关键假设、目标、约束或路线需要调整时，按共享规则提交改动及对后问的影响，不直接替换已批准方案。
- 若候选不能表达关键条件、假设被推翻、验证不充分或计算预算不匹配，应说明缺口并扩展检索、调整表达或提出替代方法，不能强行从清单选一个。涉及已批准方案实质变化时重新审核，沿用探索预算和停止条件。
